# ml/online: Gus learns from players' attacks

The fraud model behind the typed checkout. It starts from the real IEEE-CIS dataset, judges every order players send, and retrains on the orders that fooled it. A new version only goes live if it is better on players **and** no worse for real customers.

| File | What it is |
| --- | --- |
| `features.py` | The model's inputs: the IEEE-CIS columns a player's choices change (amount, product, card, distances, email domains, device, browser, proxy, hour, the C and D history counts). Constant or random game columns are left out. |
| `simulate.js` | Simulated shoppers made by the game's own code (`prototype/orders.js`): `players` (random attackers), `clever` (quiet attackers) and `honest` (the cardholders themselves). |
| `game_rows.py` | Loads simulated rows and real player orders (`server/data/ieee_rows.csv`), split by session. |
| `model.py` | LightGBM model, saved versions, thresholds, and Gus's reasons (per-order feature contributions mapped to the game's tells). |
| `train.py` | Trains v1. |
| `retrain.py` | Retrains on player orders and promotes the new version only if it passes the gate. |
| `report.py` | The attacks players found: trick families, dollars, and each version's catch rate. |
| `evaluate.py` | Day-by-day evaluation on real transactions the model never trained on: real fraud found per 100 analyst alerts (the Fraud Detection Handbook's measure). |
| `briefing.py` | An AI fraud analyst: Claude reads the numbers (versions, eval, attacks) and writes a short plain-English briefing. Falls back to a template with no API key. |
| `report.html` + `report.js` | A self-contained report page (briefing, learning-curve chart, attack families). `report.js` is generated by `briefing.py --html`. |
| `robustness.py` | Red-teams the project's own model to harden it: searches the game's checkout answers for orders Gus misses, then retrains on them (through the gate). |
| `rows.js` | Batch converter: turns a list of typed checkouts into scored rows via the game's own code, for the robustness search. |
| `probe.js` | Turns hand-written checkouts into rows, to test specific tricks. |

## Adversarial robustness (`robustness.py`)

Standard practice for a detector is to red-team it against yourself before shipping (cf. IBM's [ART](https://github.com/Trusted-AI/adversarial-robustness-toolbox)). This does that **inside the game's closed world**: it hill-climbs over the game's own checkout answers (item, who, device, where, delivery, timing) for the five victims the game deals, converts them to rows with the game's own code, and scores them with the model. It never produces anything outside the game's vocabulary; every trick it finds is one the human-player path already produces and `report.py` already names.

```bash
ml/.venv/Scripts/python -m ml.online.robustness audit    # list the model's weak spots
ml/.venv/Scripts/python -m ml.online.robustness harden   # retrain on them, through the gate
```

The point is the **harden** step: feed the weak spots back and retrain, so Gus catches them next time. A hardened version still goes through `retrain.py`'s gate, so it ships only if it stays fair to honest customers.

- **It finds what the humans find.** The search independently lands on account-takeover + gift-card codes by email as the model's blind spot — the same family human players find and the same one `report.py` marks open. That's the "humans vs machine" comparison: two different attackers, one weakness.
- **Hardening works and the gate accepts it.** In one round, the model went from catching 6% of the robustness probes to 53%, learning to watch `gift_card` and `new_address`, while real-fraud recall held (64.8% → 65.3%) and honest shoppers stayed protected. A fresh search then finds new, smaller holes — robustness is iterative, as expected.

## The report page

```bash
ml/.venv/Scripts/python -m ml.online.briefing --html   # writes report.js
```

Then open `ml/online/report.html` (any static server, e.g. `python -m http.server`). It shows the live model's real-world performance, the attacks players found, and the AI analyst's briefing. Set `ANTHROPIC_API_KEY` to have Claude write the briefing; without it, a template built from the same numbers is used. A sample `report.js` is committed so the page renders out of the box.

**Day-by-day evaluation** (`python -m ml.online.evaluate`) measures the model the way a fraud team does: on days it never trained on, reviewing a fixed number of alerts per day. v1 finds about 43 real frauds per 100 alerts and catches ~80% of each day's fraud. This is the chart's data, one line per version, so you can see whether learning from players helped or (when the gate rejects a version) would have hurt.

## Setup

**A trained `v1` ships in the repo** (`models/v1.joblib`), so a fresh clone runs the real model — judging orders and powering the checkout's gut feeling — without the Kaggle download. You only need the dataset to **retrain** or rebuild from scratch.

Run it (Python 3.10–3.14):

```bash
python -m venv ml/.venv
ml/.venv/Scripts/python -m pip install -r ml/online/requirements.txt
USE_STUBS=true ml/.venv/Scripts/python -m uvicorn server.main:app --port 8000
```

Then serve the game and open it against the API (from `prototype/`, `python serve.py`, then `http://localhost:8765/?api=http://localhost:8000`).

To **rebuild or retrain** the model, put the Kaggle files `train_transaction.csv` and `train_identity.csv` in `ml/online/data/` (git-ignored; the competition requires a Kaggle account), then `ml/.venv/Scripts/python -m ml.online.train`. Node is needed for the simulators (`simulate.js`).

## Tests

The unit tests need neither the Kaggle dataset nor a trained model, so they run fast:

```bash
PYTHONPATH=. ml/.venv/Scripts/python -m pytest ml/online/tests -q
```

They cover feature framing and encoding (unknown categories → `other`, rare values dropped), the time-ordered split and the rank thresholds, the attack-family labelling, the per-player cap and the simulated-attack weighting, and — when Node is installed — that the game's own row builder produces well-formed fraud rows.

`/submit` scores each order with the live version. `/preview` gives the checkout's gut feeling from the same score and threshold (nothing is saved), so the face and the verdict always agree: 😠 means the order would be caught. Every 25 orders that get through (`FORGED_RETRAIN_EVERY`), a retrain runs in the background. Without a trained model the server answers with the browser's scripted Gus.

## How it learns

1. **v1** trains on three kinds of rows:
   - real transactions with device info (the dataset's online segment: 144k rows, 7.8 % fraud), split by time;
   - simulated honest shoppers in the game's format;
   - simulated attackers in the game's format, weighted down to 8 % of the game-format rows, like the real fraud rate.
2. **Players attack it.** Every player order is fraud by construction, so the labels are free and can't be poisoned into "this is fine".
3. **Retrain.** The orders that got through weigh 3× (`EVASION_WEIGHT`). One player gives at most 300 rows per retrain.
4. **The gate.** On data no version trained on, the new version must:
   - catch real fraud at most 2 points less than the live version;
   - block at most 4 % of real honest customers;
   - block at most 5 % of honest game-format shoppers;
   - catch more held-out player orders than the live version, judged on at least 30 of them.

   Versions that fail are kept on record with `promoted: false`.
5. **Patch notes.** `learned` lists the tells whose share of the model's attention grew most.

## Why honest game shoppers matter

The game fills some columns in ways real data never does. For example, `dist2` is always set in the game but mostly blank in real data, and product `W` never has device info in real data. A model trained on real data plus player orders (all fraud) learns "looks like the game = fraud": a classifier separated game rows from real fraud with AUC 1.0. Adding honest shoppers in the game's format removes that shortcut. v1 blocks about 1 % of them, close to its real-world rate.

Shipping abroad records its real distance in `dist1`. A blank `dist1` is what almost every real online order has, so an abroad order used to look like a normal one.

## Two thresholds

- **The real-shop threshold** blocks 3 % of honest customers (`TARGET_FPR`). The gate and the report use it.
- **The game threshold** depends on rank (`RANK_CUTOFF`):

  | Rank | Gus blocks orders he's at least this sure are fraud |
  | --- | --- |
  | Rookie | 90 % |
  | Hustler | 80 % |
  | Schemer | 65 % |
  | Operator | 50 % |
  | Mastermind | the real-shop threshold |

  As versions learn, the same tricks score higher, so the game gets harder.

## v1 numbers (seed data, Oct 2026)

- **Real test (last 15 % of days):** catches 64.8 % of fraud and blocks 3.7 % of honest customers. Only the columns the game can fill are used.
- **Clever simulated attackers caught, by rank:** 49 % (Rookie) → 79 % (Mastermind). Random attackers: 75 % → 93 %.
- **One retrain on 400 clever simulated sessions:** held-out clever orders caught 79 % → 95 %, real recall 64.8 % → 63.3 %, honest game shoppers blocked 1.3 % → 4.4 %.

## Known limits

- The column mapping in `prototype/orders.js` (`toRows`) is a documented guess, because IEEE-CIS columns are anonymized.
- The simulated honest shoppers' habits (how often they use a VPN or ship elsewhere) are assumptions, and they set how suspicious "ships elsewhere" looks.
